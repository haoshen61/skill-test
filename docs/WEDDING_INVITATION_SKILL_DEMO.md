# Wedding Invitation Builder：比赛演示流程（8–12 分钟）

这是一份可照着执行的现场 runbook。演示目标不是播放一张静态截图，而是让评委看到一条完整链路：偏好采集、设计决策、移动页面、宾客数据、后台管理和安全发布。

## 1. 演示前准备

在仓库根目录执行：

```bash
git status --short --branch
git pull --rebase origin main
npm --prefix skill test
node skill/scripts/create-invitation.js --assets assets --brief demo/confirmed-brief.json --out /tmp/wedding-invitation-builder-preview
```

这段命令适用于干净的演示 clone；若 `git status` 显示另一台电脑的未提交工作，先保留并处理这些改动，不要强行切换分支或覆盖文件。

若之前用完整 SSH URL 推送，先 fetch 实际远程并比较提交，不能凭过期 `origin/main` 的 ahead 数量判断是否推送。本演示默认仅操作本地 mock；实际发布范围取自当前任务及已有授权，不在每一步重复询问。

用任意静态 HTTP 服务器打开 `/tmp/wedding-invitation-builder-preview/index.html`，在手机视口 390×844 和桌面视口检查页面；`admin.html` 是当前浏览器 localStorage 的只读演示页。素材位于 `assets/`，不是生产运行时资源。

## 2. 逐段脚本

### 0:00–0:45：问题与触发

对评委说：

> 普通模板只解决“放一张照片和一段文字”，没有把两个人的表达方式、宾客数据和发布安全放在同一条链路里。这个 skill 从一句自然语言请求开始，把它变成可运行的邀请函。

示例触发：

> 请帮我做一份手机优先的婚礼邀请函。新郎习惯用代码表达，新娘是插画师；主色浅米色，粉色和蓝色只做局部重点色，需要 RSVP、点歌和后台管理。

### 0:45–2:00：展示一问一答的采集

不要一次抛出问卷；演示 skill 依次追问：

1. 日期、时区、婚礼形式和签到/仪式时间？
2. 场地的短名、宴会厅和完整地址是否已确认？
3. 新人姓名和希望显示的身份标签是什么？
4. 两人的故事想保留哪一条关系弧线？
5. 哪些图片/音乐允许进入仓库，是否允许压缩、调色或 AI 处理？
6. RSVP 只登记到场人数，还是也收集缺席祝福？是否需要点歌？
7. 是否有 Git 远程、后端环境和域名；现在是否授权生产发布？

特别演示一次地址冲突：如果用户给出两个不同门牌号，skill 会停下来列出冲突，而不是猜测。

### 2:00–2:45：生成 brief

展示一页 brief 摘要：

- 米色大面积底色，咖色负责正文/边框。
- 粉色、蓝色只占小比例，用于时间、按钮或局部弥散形状。
- 中文细宋体/STSong，英文 Avenir，装饰性英文少量 SnellRoundhand。
- 代码打字机与插画/照片并列，但手机改为单栏。
- 封面 → 关于我们 → 婚礼信息 → RSVP → 音乐留言 → 感谢。

指出：这份 brief 是可审阅的中间产物，修改色彩或文案时可以重新生成，不需要从头猜设计。

### 2:45–4:30：手机端真实交互

1. 先展示“婚礼邀请函”、新人和婚礼信息；未来邀请函不默认进入回顾页。手机相册为足宽单栏，展示慢网加载时的中性占位：请求结束前不会先出现任何私人照片，空列表或失败后才按设计回退。
2. 展示米色纸张颗粒、弥散圆弧和响应式排版；代码打字机、路径和花瓣等目标若超出当前便携生成器能力，必须在 pending 中说明。
3. 滑到抽象相册区域，左右翻页；切换音乐按钮，说明浏览器可能阻止自动播放，按钮是可靠兜底。
4. 强调日期、签到/仪式时间和场地层级；地图/地址以用户确认值为准。
5. 如需展示回顾分支，另用 `mode: "recap"` 的 brief 生成一次，说明这是显式选择而非默认行为。

### 4:30–6:00：RSVP 与点歌闭环

1. 填写一个明确的演示姓名、手机号后四位和大人人数，提交。
2. 使用相同姓名和后四位改人数，再提交；展示管理页仍只有一条记录，说明幂等更新。
3. 添加一首歌和留言，说明到场与否都欢迎点歌；页面只收集必要信息。
4. 打开 `admin.html`：展示当前浏览器中的本地 RSVP/点歌数据。它没有生产认证、云端幂等或 CSV 导出能力。

不要使用真实宾客手机号或真实敏感信息。演示结束后清除本地 mock 数据或重启服务器。

### 6:00–7:00：发布边界

1. 展示 `release-record.json` 的 `publish=false` 和 pending 列表。
2. 说明分享卡片、通知页、CloudBase/Cloudflare、生产认证、真实多用户幂等和图片处理不在这个隔离仓库中。
3. 说明后续 provider 适配必须先确认环境、密钥位置、域名、素材授权和生产授权；Git push、生成目录和本地演示都不等于发布。

### 7:00–8:30：质量与发布闸门

展示命令结果：

```bash
npm --prefix skill test
```

解释三个边界：

- Git push：只同步源码和 demo 资产。
- Cloudflare Workers Static Assets：只有用户明确提供目标并授权时，才按 provider 说明构建和上传静态文件。
- CloudBase：新数据库、逻辑桶/CORS 和函数先就绪，验证真实上传后才发布依赖新动作的前端；只改布局时跳过后端。

最后说：已有明确的迁移和发布授权可以连续执行，不需要逐步重新确认；本次比赛演示只到已验证的本地构建目录。设计稿中的 `ReleaseRecord` 分别记录源码、后端与静态发布状态。

需要解释运维时，展示 [设计稿的发布闸门](WEDDING_INVITATION_SKILL_DESIGN.md#release-gate) 和 [provider 说明](../skill/references/provider-release.md)，不在比赛中临时改生产配置。实际生产 CORS/签名仍需线上验收，本地 mock 不能证明它们通过。

## 3. 现场评分点

| 评委看到的证据 | 对应能力 |
| --- | --- |
| 只问一个问题，下一问随回答变化 | 对话式需求发现 |
| brief 中有色板、字体、布局和待确认项 | 可解释的设计决策 |
| 手机页面可翻页、默认邀请标题和信息可见 | 可运行的前端产物 |
| RSVP 重复提交只更新一行 | 数据契约与幂等性 |
| 管理页统计、编辑、CSV、点歌审核 | 真实的宾客数据闭环 |
| `admin.html` 明确是当前浏览器的本地只读演示页，不冒充生产后台 | 本地数据边界 |
| 资源白名单、分享卡片测试、构建结果 | 发布可靠性 |
| 按已有授权和任务范围执行、凭据只记录位置 | 范围控制和配置保护 |

## 4. 断网与故障预案

- **CloudBase 不可用**：保持本地 demo，并说明生产适配器未被改变。
- **自动播放失败**：点击播放按钮；这是浏览器策略，不是数据故障。
- **图片加载缓慢或失败**：请求中使用中性加载占位；请求完成后区分真实照片、空列表和失败，再决定是否回退。静态演示图查 manifest；动态图检查公开列表和临时 URL 是否有效，不把签名 URL 写进报告。
- **上传提示无法连接或操作不存在**：分别检查是否把大图作为 JSON 发到网关，以及函数是否已部署新动作；不要把两者都当作断网。线上处理见 CloudBase 部署文档，现场继续用 mock。
- **生成失败**：停在错误信息，修复后重新运行 Skill 测试；不要手工复制文件到输出目录。
- **地址或日期被评委临时修改**：回到 brief，重新确认共享页面、通知页和分享卡片，再执行测试。
- **远程 main 有新提交**：先 `git pull --rebase origin main`，解决冲突后再提交；不 reset、不 force push。

## 5. 演示后交付

记录以下信息：

- 演示使用的 commit、测试数量和构建目录。
- 使用了哪些 demo 资产，以及它们是否仅限私有仓库/比赛演示。
- 若执行生产发布：分别记录所需迁移及查询结果、CORS/上传验证、函数更新记录、Cloudflare deployment ID/时间、正式 URL、验收和回滚目标；未涉及的阶段记为未执行，不沿用历史结果冒充本次验证。
- 若没有生产授权：明确写“只完成本地验证，未上传生产”。

演示结束后不要把真实宾客资料、密钥、管理员密码或高分辨率原稿加入 Git。资产包中的 `manifest.json` 是来源和权限记录，不是生产配置。
